# APT 数据处理组件 PRD

**版本：** v0.1  
**项目阶段：** MVP  
**产品定位：** 为 APT Investigation Agent 提供统一、可查询、可追溯的安全数据服务。

## 1. 项目背景

企业安全环境中存在大量异构数据：

- 终端数据：进程、文件、认证、网络连接、系统活动。
- 网络数据：流量、DNS、连接记录。
- 安全设备：防火墙、WAF、IDS/IPS。
- 身份数据：用户、账号、权限、认证记录。
- 资产数据：主机、容器、服务、云资源。

这些数据来源不同，字段定义不同，实体标识也不同。

本项目希望建立一个独立的数据处理组件，将不同来源的安全数据转换成统一的安全事件，并建立实体及其交互关系，最终形成可查询、可追溯的安全事实空间。

该组件不负责攻击研判，主要服务于后续 APT Investigation Agent。

## 2. 产品目标

实现以下能力：

1. 支持多种安全日志接入。
2. 将原始日志解析并映射为统一 OCSF 事件。
3. 识别事件中的实体，并解决实体身份归一化问题。
4. 根据事件语义提取实体之间的交互关系。
5. 建立可查询的实体关系图。
6. 保留事件、图关系与原始日志之间的追溯关系。
7. 提供统一的数据查询 API（并配套查看与调试用 Web 控制台）。

核心原则：

- 优先复用行业成熟标准，不重复发明安全事件 Schema。
- 优先使用确定性程序处理数据。
- 不把未经证实的推断写成客观事实。
- 原始数据不可丢失，标准化结果可重建。
- 数据处理组件与 Agent 解耦。

## 3. 整体架构

数据处理流程：

原始数据源 → 数据接入 → 日志解析 → OCSF 标准化 → 实体识别 → 关系提取 → 图构建 → 数据存储 → 查询 API

### 3.1 数据接入层

MVP 优先支持：本地 JSON / JSONL 文件、CSV 文件、Sysmon 事件样本、Zeek JSON 日志、资产清单数据。  
后续扩展：Kafka、Syslog、HTTP API、其他 SIEM / XDR 接口。  
接入要求：记录数据来源、记录接收时间、保留原始内容、支持重复数据识别、记录解析失败和接入失败。

### 3.2 日志解析层

职责：识别日志格式、提取原始字段、处理时间格式、识别日志来源、输出统一的中间结构。Parser 不负责攻击判断。

### 3.3 OCSF 标准化层

以 OCSF 为首选标准（https://ocsf.io/）。优先支持：
- Process Activity
- File System Activity
- Network Activity
- Authentication
- DNS Activity
- Application Activity

要求：使用标准 OCSF 字段、保留 OCSF 版本信息、保留原始事件 ID、未映射字段放入扩展字段或保留原始数据、不支持的事件不能静默丢弃。

### 3.4 实体识别层

第一批实体：

| 实体 | 关键属性 |
|---|---|
| Host | hostname、IP、OS、资产 ID |
| Process | Process GUID、PID、路径、命令行 |
| User | 用户名、UID、SID、域 |
| File | 文件路径、Hash |
| Network Endpoint | IP、Port、Protocol |
| Service | 服务名称、监听端口 |
| Container | 容器 ID、Runtime |

要求：同一实体可能被不同日志源描述；不能仅凭名称相同就认定是同一个实体；PID 必须结合主机和进程生命周期处理；IP 地址需要考虑 DHCP、NAT 和地址复用；实体合并必须保留依据；无法确定身份的实体允许暂时独立存在。

### 3.5 关系提取与图构建层

第一批关系：

| 关系 | 含义 |
|---|---|
| RUNS | 主机运行进程 |
| SPAWNS | 进程创建子进程 |
| READS | 进程读取文件 |
| WRITES | 进程写入文件 |
| CONNECTS_TO | 进程建立网络连接 |
| AUTHENTICATES_TO | 用户或进程向服务认证 |
| ACCESSES | 主体访问资源 |
| RESOLVES | DNS 查询及解析关系 |

关系要求：每条关系必须有来源事件；保留发生时间；保留关联依据；区分确定性关联和候选关联；不根据单纯时间接近建立确定性因果关系；多条日志描述同一次交互时允许聚合，但必须保留全部原始证据。MVP 暂不引入独立的攻击假设图。

### 3.6 数据存储层

逻辑上区分三类数据：**原始事件**、**标准化事件**、**实体关系**。  
选型依据是数据规模、关系查询复杂度、写入性能和维护成本，而不是预先认定必须使用图数据库。

## 4. 查询服务

第一批接口：`search_events`、`get_event`、`get_entity`、`get_entity_relations`、`traverse_graph`、`get_relation_evidence`。  
所有查询必须支持权限范围、时间范围和结果数量限制。后续可在 API 之上增加 MCP Server，MCP 不属于数据处理核心。

## 5. 非功能需求

- **数据可靠性**：重复数据不能产生重复实体和重复关系；数据接入失败必须有明确记录；处理过程支持重试；原始日志可以重新解析和重建图。
- **可追溯性**：每条标准化事件可以追溯原始日志；每条关系可以追溯支撑它的事件；实体合并有明确依据；不确定的关联不能伪装成确定事实。
- **可扩展性**：新数据源通过 Adapter 扩展；新事件类型通过 Schema Mapping 扩展；新实体和关系类型不应要求修改整个处理框架。
- **可观测性**：记录接入数量、解析成功率、标准化失败率、实体合并数量、关系生成数量、重复率、处理延迟和查询耗时。

## 6. MVP 范围

本次不做：完整 SIEM 检测引擎、Sigma 规则执行引擎、IOC 情报平台、LLM 语义研判、APT 攻击假设管理、Agent Runtime、自动化安全响应、大规模分布式部署。

## 7. 验收标准

1. 原始日志能够成功接入并保留。
2. 支持的日志可以正确映射到 OCSF。
3. 同一进程的不同事件可以通过稳定身份关联。
4. 进程创建关系可以正确生成。
5. 进程网络连接可以正确生成。
6. 防火墙与终端连接记录可以根据可靠字段关联。
7. 一条图关系可以反向找到对应原始日志。
8. 重复导入不会重复创建实体和关系。
9. 无法确定的关系不会被强制合并。
10. 可以通过 API 查询实体及其关系。

## 8. 开发里程碑

- M1：工程骨架、数据模型和接口定义。
- M2：JSON / JSONL / CSV 接入及 Parser。
- M3：OCSF 标准化和字段映射。
- M4：实体识别、实体归一化。
- M5：关系提取与图构建。
- M6：存储和查询 API。
- M7：使用测试数据进行端到端验收。
